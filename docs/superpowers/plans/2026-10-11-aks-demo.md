# AKS development demo implementation plan

> **For agentic workers:** Use superpowers:executing-plans inline. Track progress in todos.md.

**Goal:** Run the existing frontend and backend on a small, temporary AKS cluster within the user's $5 spending constraint.

**Final status:** Superseded by the user's App Service deployment request. The one-node cluster and registry were provisioned, then both dedicated resource groups were deleted and verified absent. Kubernetes application rollout and forwarding were cancelled. Frontend/backend are deployed and verified on Free F1 App Service; see [deployment guide](../../azure-app-service.md).

**Architecture:** One fixed Linux node on AKS Free tier; one replica of each application; ACR Basic for images. ClusterIP services stay private and kubectl forwards the frontend to localhost:8080; nginx forwards /api to Express. Supabase remains the database. Delete the dedicated demo resource group after inspection.

**Tech stack:** Existing Node 24 Dockerfile, unprivileged nginx frontend image, Kubernetes Deployments/Services, Kustomize and Azure CLI.

**Spec:** User request on October 11: deploy both services to Azure Kubernetes for learning, no scaling, maximum $5 budget. Subscription details are supplied in chat; no Azure authentication is available yet.

## Constraints and review focus

- Never create a persistent cluster on a $5/month assumption. Verify time-limited demo agreement and cleanup scope first.
- Keep existing Supabase data intact; cleanup targets only a newly created, dedicated demo resource group.
- No public app listener, TLS/domain purchase, autoscaler, additional database, CI pipeline or paid log workspace for this demo.
- No service-role key, registry password or .env copied into either image; public Supabase build variables only.
- Do not write a provisioning wrapper: use reviewable CLI commands and stop immediately if any command fails.
- Verify image build, probes, runtime user, SPA fallback, proxy and resource limits before claiming remote deployment.

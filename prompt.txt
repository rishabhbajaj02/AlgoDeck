

\# Build a Full-Stack Adaptive Practice & Revision Platform  Act as a senior full-stack architect and engineer. Build a complete, working application from frontend to backend, including database persistence, authentication, adaptive scheduling, logging, testing, and deployment documentation.  Do not create just a UI mockup. All major features must work end to end.  Inspect the existing repository before making changes. If starting from scratch, create the project structure described below.  ## 1. Product overview  Build a reusable Adaptive Practice & Revision Platform.  Users can create collections of questions, import question lists, complete daily practice sessions, rate each question Easy, Medium, or Hard, and automatically receive revision questions based on their performance history.  Initial use cases include: - DSA questions grouped by patterns such as sliding window, graphs, and dynamic programming. - System design interview questions. - Technical interview preparation. - Language-learning questions and flashcards. - Arbitrary user-provided question lists.  The scheduling engine must be independent of DSA-specific concepts.  Core product promise: practice a configurable number of questions each day, revisit difficult questions more frequently, and gradually reduce review frequency for mastered questions.  ## 2. Technology stack  ### Frontend - React with TypeScript. - Vite for development and production builds. - React Router for navigation. - TanStack Query for server-state management and API caching. - React Hook Form and Zod for forms and client-side validation. - Tailwind CSS and a consistent component library such as shadcn/ui. - Recharts for progress visualizations. - Vitest and React Testing Library for frontend tests.  Use reusable components, accessible interactions, loading states, error states, and responsive layouts.  ### Backend - Node.js with TypeScript. - Express.js REST API. - Zod for request and environment-variable validation. - A modular, service-oriented architecture. - Supabase JavaScript client where appropriate. - Supabase PostgreSQL accessed through a clearly defined persistence layer; use Supabase's supported database tooling and parameterized queries. - Vitest for unit tests and integration tests, with Supertest for HTTP endpoints.  Use strict TypeScript settings. Avoid \`any\` unless there is a documented reason.  ### Database and authentication - Supabase PostgreSQL for persistent application data. - Supabase Auth for registration, login, logout, and session management. - Supabase-issued access tokens validated by the backend. - Database schema migrations committed to the repository. - Row Level Security (RLS) policies for user-owned data. - Seed scripts for development and testing.  The React frontend must never contain the Supabase service-role key or other privileged secrets.  The backend must never trust a user ID supplied in a request body as proof of identity. Derive the authenticated user ID from a verified access token.  Never disable RLS merely to make application queries work. Document how backend database access interacts with RLS and enforce authorization on every relevant operation.  ### Logging and observability - Use Pino for structured JSON logging. - Add HTTP request logging using pino-http or an equivalent. - Generate or propagate request correlation IDs. - Include request method, route, status code, duration, and safe contextual identifiers. - Add centralized error-handling middleware. - Log database failures, scheduling decisions, authentication failures, and unexpected exceptions. - Configure development-friendly logs and production-compatible log output. - Never log passwords, access tokens, refresh tokens, API keys, database connection strings, or sensitive request headers. - Make log verbosity configurable through environment variables.  Document how logs can be exported to a centralized logging service in production.  ## 3. Database schema  Create normalized PostgreSQL tables with UUID primary keys, foreign keys, appropriate indexes, timestamps, and constraints.  ### collections - id - user_id - name - description - daily_target, default 5 - new_question_limit - review_policy configuration - created_at - updated_at  ### questions - id - collection_id - user_id - title - content - category - pattern - source_url, nullable - metadata, JSONB - created_at - updated_at - archived_at, nullable  Support custom fields through metadata without hardcoding one question format.  ### question_progress - id - user_id - question_id - last_shown_at - last_rated_at - next_review_at - last_rating - current_priority - ease_factor - consecutive_successes - consecutive_difficult_ratings - total_attempts - successful_attempts - created_at - updated_at  Enforce a unique constraint on user_id and question_id.  ### practice_sessions - id - user_id - collection_id - session_date - status - target_question_count - created_at - completed_at  Enforce one session per user, collection, and study date.  ### session_questions - id - session_id - question_id - position - status - selected_at - completed_at - rating  Enforce uniqueness of question_id within a session and uniqueness of position within a session.  ### question_attempts - id - user_id - question_id - session_id - rating - attempted_at - time_spent_seconds, nullable - notes, nullable - scheduling_snapshot, JSONB  Store each completed attempt as an immutable historical record.  ### audit_events - id - user_id, nullable - event_type - request_id - entity_type, nullable - entity_id, nullable - safe_metadata, JSONB - created_at  Use audit events for meaningful application actions, not as a substitute for operational logs. Avoid recording secrets or unnecessary personal data.  Create appropriate indexes for user ownership, collection lookups, due review dates, session dates, and attempt history.  Use foreign keys and delete behavior that prevent accidental deletion of historical records. Implement collection deletion as a deliberate, documented operation.  ## 6. Question collection management  Users must be able to: - Create, edit, archive, and delete collections. - Add questions manually. - Edit and delete questions. - Assign categories and patterns. - Search and filter questions. - Import questions from CSV or JSON. - Export a collection. - View question counts by category and review status.  CSV import should support at least: - title - content - category - pattern - source_url  Validate uploaded content, impose sensible file and row limits, report row-level errors, and avoid duplicate imports when possible.  Support a JSON import format with documented examples.  Do not scrape external websites or assume a URL contains structured question data. The MVP only needs manual entry, paste, CSV, and JSON imports.  ## 7. Daily practice session  The user chooses a collection and receives the configured number of questions, defaulting to five.  The selection engine should consider: 1. Unseen questions. 2. Questions due for review. 3. Overdue questions. 4. Difficulty and historical ratings. 5. Questions already shown in recent sessions. 6. The collection's new-question limit. 7. The user's daily target.  The default selection policy should guarantee that a question shown in yesterday's session is not shown in today's session, even if it is overdue.  Do not permanently exclude such questions. Preserve their overdue priority and make them eligible in a later session.  Generate and persist the session before returning it to the client. A repeated request for the same user, collection, and study date must return the existing session instead of generating a new set.  Use a database transaction or an equivalent concurrency-safe mechanism to prevent duplicate sessions and duplicate selections under concurrent requests.  Handle insufficient eligible questions explicitly. Return the available count and a clear explanation instead of silently breaking the no-consecutive-day rule.  The interface should support: - Viewing one question at a time. - Revealing hints or solutions when provided. - Opening the original problem URL. - Marking a question complete. - Rating Easy, Medium, or Hard. - Optional time spent and notes. - Moving between questions. - Resuming an incomplete session. - Viewing a completion summary.  Persist progress after every rating, not just when the entire session finishes.  ## 8. Adaptive scheduling algorithm  Implement the scheduling engine as a dedicated, independently testable service.  Use two distinct concepts:  A. Review eligibility: when the question becomes due.  B. Selection priority: how likely the question is to appear among eligible candidates.  Start with configurable intervals:  - Hard: 1 day. - Medium: 3 days. - Easy: 7 days.  After repeated successful reviews, progressively increase intervals. For example: - Hard: 1, 2, 4, 7 days. - Medium: 3, 5, 10, 20 days. - Easy: 7, 14, 30, 60 days.  These are initial heuristics, not scientifically validated optimal intervals.  Define a documented weighting function such as:  weight =   difficultyWeight   \* overdueMultiplier   \* failureMultiplier   \* recencyAdjustment  Initial difficulty weights: - Hard: 4. - Medium: 2. - Easy: 1.  Increase priority for repeatedly difficult questions and overdue reviews. Reduce priority for questions that have been repeatedly solved successfully and extend their next review interval.  Use weighted random selection without replacement for a single session.  Normalize selection probabilities over the eligible pool.  Ensure the scheduler: - Is deterministic in unit tests when given a fixed random seed. - Never selects a question twice in the same session. - Respects consecutive-day exclusions. - Handles empty pools and small collections. - Does not accidentally mark an unanswered question as easy. - Preserves overdue priority when a question must be skipped. - Stores enough history to recalculate schedules in future algorithm versions.  Keep the scheduling policy configurable so alternative algorithms can be introduced later.  ## 9. Frontend pages  Build these complete pages:  ### A.
